# Sandhya mobile app and launch-readiness audit

**Audit date:** 29 September 2026  
**Repository:** Sandhya  
**Reviewed revision:** main at aaada4d3756c0ac157c3d61de5bc5a301b505270  
**Audit mode:** read-only repository, history, build, test, content, UX, security, and viability review

## Executive verdict

Sandhya is not ready for a public App Store/Google Play launch or a paid Navratri launch.

The repository is a credible engineering preview: the mobile app has a coherent Expo/React Native structure, the backend has strong source-level controls, the content tooling is unusually careful about provenance, and the core static content experience can be useful offline. The project is not yet a launchable product because the customer-facing promise, trusted content, paid offer, native release path, and operating evidence are not closed.

The practical status is:

| Area                                     | Verdict                               | Evidence                                                                                                                                              |
| ---------------------------------------- | ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Internal or tightly limited free preview | **Possible with caveats**             | Mobile build, web export, typecheck, scoped lint, backend checks, and 238 tests pass.                                                                 |
| Public free store launch                 | **No-go today**                       | Production configuration, legal/support URLs, native device QA, accessibility testing, analytics, content trust, and release evidence are incomplete. |
| Paid Navratri 2026 challenge             | **Hard no-go**                        | The catalog is unpublished, has zero written sessions, has blank price, and has no audio or cleared paid corpus.                                      |
| Live Ask feature                         | **No-go and out of pilot scope**      | The plan cuts scoped AI; the UI remains visible while the prepared RAG corpus is missing.                                                             |
| Subscription monetization                | **No-go**                             | The plan says one-off challenge revenue while the app still exposes monthly, annual, and lifetime Plus plans.                                         |
| Product viability                        | **Promising hypothesis, unvalidated** | There is a plausible trust/pronunciation wedge, but no repository evidence of activation, retention, willingness to pay, or acquisition conversion.   |

This is not “the idea has zero viability.” It is “launch readiness is effectively zero for the paid product currently described.” The next sensible shipment is a narrow, free, instrumented preview after the P0 trust and release gates below.

## 2. Architecture and user/data flow

The architecture is coherent and follows the fixed v1 direction:

1. Expo Router presents the mobile/web client.
2. Native state uses Zustand and TanStack Query.
3. Supabase Auth provides identity; Postgres/RLS stores user and content data.
4. Edge Functions handle account operations, Ask, payments/webhooks, notifications, admin work, and RAG.
5. Content tools validate Markdown and generate static/bundled JSON or SQL.
6. pgvector retrieval is intended to feed a structured server-side answer.
7. RevenueCat and Expo Notifications are native integrations.
8. A static web builder generates explanatory/SEO pages; an admin app exists separately.

The intended authenticated AI path is:

mobile Ask UI -> authenticated Edge Function -> safety/quota/cache -> rights-filtered retrieval -> provider -> structured answer -> audit message

The intended content path is:

approved Markdown -> content-tools validation -> generated mobile bank/SQL -> local fallback or Supabase content -> sourced UI

The architecture is stronger than the current product state. The critical issue is not that the system has no design; it is that several design layers are incomplete or contradictory at the point a user would encounter them.

### Requested surface coverage

- **Search:** no complete dedicated search route/service was identified. Users can browse curated content and use Ask when enabled, but there is no verified general search experience with loading, empty, offline, and ranking states.
- **Forms and input:** onboarding, sign-in, recovery, journal, Ask, feedback, account deletion, and settings inputs exist. Validation is generally present, but keyboard avoidance and error/retry feedback are incomplete on some paths.
- **Notifications/background tasks:** local and remote notification code exists, including a scheduled daily-reflection worker. Festival reminders use a generic local time; production scheduling, push receipts, and invalid-token behavior are unverified.
- **File/media handling:** there is no camera, microphone, location, contacts, Bluetooth, or biometric product flow and no corresponding unnecessary permission found. Audio is a required product capability but no audio assets/player are present.
- **Deep links:** the custom sandhya scheme and auth callback are configured at source level. Universal Links/App Links and provider allowlists were not verified.
- **Loading/empty/error/retry:** many primary states exist, but remote detail routes can flash unavailable, account hydration can fail silently, and content fallback lacks a retry action.
- **Lifecycle:** root auth refresh/AppState handling exists. Challenge polling is not paused/capped, and signed-build resume behavior is unverified.
- **Orientation/safe areas:** portrait orientation and safe-area utilities are configured; tablet, notch, Dynamic Type, and keyboard behavior lack a complete physical-device matrix.
- **Observability:** consent-gated client telemetry and generic backend observability exist, but the activation, retention, purchase, challenge, audio, and share events needed for launch decisions are missing.

## 4. Data architecture and lifecycle

### Content data

- The generated mobile shloka bank has 661 approved entries and is about 3.7 MB.
- The source tree contains 1,870 shloka Markdown files: 661 marked approved and 1,209 draft; the generator skips drafts.
- Curated dynamic content is fetched from Supabase with bundled/local fallback.
- Query defaults use a five-minute stale time and one retry.
- Daily reflection selection uses an ordered maybeSingle query and is not fully personalized to the user’s declared tradition.
- Detail routes can check fallback data before the remote query has completed, producing a false unavailable state.

### Account lifecycle

The account lifecycle has a reasonable shape:

guest -> optional onboarding preferences -> sign-in -> profile/preferences -> remote journal/saved/activity/conversations -> export/delete

Risks:

- Onboarding answers and language remain device-owned after sign-out. That may be intentional, but on a shared device it can leak personalization into another account.
- setSavedItems unions remote IDs into existing local IDs rather than replacing them. A server-side deletion can therefore remain locally visible.
- Account hydration errors are silently discarded in the root layout.
- Export/delete paths exist and are source-level protected, but live deletion ordering and provider-side retention are unverified.

### Journal lifecycle

The local journal is split into chunks with an index and a scope. This is a sensible way to stay within storage limits, but writes are not transactional:

1. A new prefix/chunk set is written.
2. The index is updated.
3. The previous prefix is deleted.

Concurrent save/remove/clear operations can interleave and cause lost updates or orphaned chunks. In authenticated mode, any remote insert error falls back to local storage. That makes offline resilience convenient but hides authorization, schema, and outage failures from the user and telemetry.

### Cache and synchronization

- TanStack Query provides server cache/retry behavior.
- Local content fallback is useful for read-heavy experiences.
- There is no general offline banner, explicit retry action, or consistent stale/queued-write state.
- Conversation history and some account data are network-dependent.
- The challenge confirmation loop is a battery/network risk because it is not lifecycle-aware.

## 6. Content correctness, rights, and trust

### Strong foundations

- Content validators require structured verse fields including Devanagari, IAST, a reading field, meaning, and source.
- The challenge document type is frozen with six ordered sections and can_embed: false.
- Tradition and regional variation fields are rendered from actual database data in the current content helper.
- The current production surfaces contain no match for the forbidden competitor app name; historical planning references are confined to internal documents.
- No AI-generated devotional/deity imagery was introduced by this audit.

### Hard blockers

The validator’s review_status: approved is not equivalent to commercial rights approval. The audit found:

- 250 approved files containing “pending review”.
- 167 approved files containing “translation pending”.
- 494 approved files containing “draft originals”.
- 167 approved files containing “conversion pending”.
- 210 approved files carrying non-commercial or personal-study language.
- Zero audio assets in the repository.
- The rights tracker has only one approved data row.

This is a release-blocking mismatch. Before charging, every shipped source needs a rights row covering translator, URL, copyright status, storage rights, excerpt rights, and embedding rights. The free/non-commercial exception in the rights memo must not silently become paid distribution.

### Verse attribution

The shloka type has source but no mandatory named translator. The shloka detail, chapter reader, and text detail can therefore render a quote without meeting the product rule that every quoted verse names a translator and source. Make attribution a hard schema/validator requirement and render it in every quote surface.

### Festival dates

The current UI can render reckoning, location, source, and disagreement, but community remains optional in both type/parser and display. A split observance must name the observing community. Do not publish a date unless all four are present:

1. amānta or pūrṇimānta reckoning;
2. named observing community where practice splits;
3. computed location;
4. source and disagreement.

The calendar also says local timings are not calculated yet. That must be explicit in product copy and excluded from any claim that the app provides local observance timing.

### Audio

Audio is a core product requirement and the clearest public trust wedge. Data parsing has fields for audio, but there are no audio files and no player, adjustable speed, clear reading, or slow repeat-after-me interaction. This is not a “nice-to-have polish” gap; it removes the feature that lets a stranger verify value in thirty seconds.

- Result: six finding records grouped into three actionable families

### Actionable security families

1. **Browser storage:** native SecureStore is good, but the web fallback uses script-readable localStorage for persistent auth/session material and private journal data. Do not treat the web preview storage path as a production security equivalent. Either disable authenticated web use, isolate it, or move to a web-specific cookie/session design with a strict CSP.
2. **Challenge progress:** an authenticated participant can directly insert an in-range completion row without server-validating configured session existence, approved review state, unlock date, or lifecycle timestamp. This is currently a low-impact self-owned integrity issue, but it becomes important if progress drives rewards, eligibility, or social proof.
3. **Request-body resource limits:** public Ask/webhook handlers can clone/read bodies before reliable application limits. Chunked or missing-content-length requests can be buffered before rejection. Add a bounded streaming reader and enforce platform/rate limits before parsing.

### Security positives

- No tracked .env or provider secret was found.
- Public Supabase/RevenueCat/PostHog/Sentry identifiers are treated as public configuration; service-role/provider secrets remain server-side in source.
- RLS and migration security checks pass.
- PKCE and Supabase auth refresh handling are present.
- Client telemetry is consent-gated and avoids logging full prompts/responses.
- Account export/delete and user ownership checks exist.
- Native permissions are minimal; no unnecessary camera/location permission was added.

### Privacy limitations

The source review cannot confirm:

- production Supabase retention and log settings;
- provider retention/training settings;
- deployed web CSP and cookie flags;
- store privacy labels and data-safety declarations;
- RevenueCat, Expo push, PostHog, or Sentry production configuration;
- live RLS behavior after migrations.

## 8. Accessibility, localization, and user experience

### High-priority UX issues

- Onboarding is six to seven questions on the shortest/longest tested paths, plus interstitial/result screens, rather than the planned three-question first-use path.
- Home and Calendar seven-cell rows require 336px before padding; a 320px phone has only 288px available.
- Valid Supabase-only detail routes can briefly show unavailable before fetch completes.
- Large journals, saved items, conversations, and messages are rendered with unbounded ScrollViews instead of virtualized lists.
- Android Ask input is absolutely positioned without KeyboardAvoidingView.
- Challenge purchase polling runs every three seconds without maximum duration, backoff, or AppState pause.
- Challenge completion errors are not consistently surfaced.

### Accessibility gaps

- Calendar announcements omit month/year and reckoning context.
- Practice back arrow has no accessible label.
- Root loading spinner has no accessible status label.
- Content fallback notice has no retry action.
- Dynamic Type, VoiceOver, TalkBack, 320px, and reduced-motion behavior lack focused tests.

### Localization

The i18n module currently contains English only and always returns English UI copy. The settings language choice changes some verse translation/meaning behavior but does not localize the interface. Either label the setting accurately as content language or finish a real localization path; do not imply Hindi/other UI support that does not exist.

### Appearance and platform

app.json declares a light-only UI. That can be an intentional v1 decision, but it should be tested for contrast and low-light use rather than treated as complete platform behavior. Tablet support is declared; a tablet review was not performed.

## 12. Product usefulness and market viability

This section answers the clarified question: whether the product is viable, works well for users, and is ready to launch—not only whether it has commercial/legal risk.

### The strongest user job

The best product hypothesis is not “another AI spirituality app.” It is:

> Help someone who inherited a Hindu practice understand why it is done, learn a trustworthy source, and say it correctly.

That job is specific, culturally respectful, and aligned with the project’s own competitive analysis. It also gives a stranger a fast test: open a verse, hear a clear reading, see the source/translator, and understand the practice variation.

### What currently works for a user

- Static/bundled content can be available without a network.
- The app has a calm, coherent daily-practice structure.
- Onboarding uses answers to route content rather than collecting entirely decorative survey data.
- Festival and tradition variation are treated more carefully than typical competitor patterns.
- Journal and saved-item concepts support repeat use.
- Backend safety, quota, citation, and audit architecture is more mature than the visible pilot scope.

### What currently fails the user promise

- The pronunciation wedge has no audio.
- A quoted verse may not show a named translator.
- Festival dates can lack a named community or local timing computation.
- Ask appears available even though its corpus and pilot scope are not ready.
- The challenge page presents a finite paid journey with no sessions.
- Onboarding asks too much before the first meaningful content interaction.
- The web product is not a path from discovery to install or waitlist.
- Error and offline states often do not tell the user what happened or how to recover.

### Time-to-value

The first useful verse is delayed behind welcome, intent, household, branch, script, language, reminder, name, and result screens. The result screen is good, but it comes too late. The first-use path should be:

1. choose one essential intent or skip;
2. show one sourced verse/practice immediately;
3. offer clear audio and one action;
4. progressively ask for language, reminder, name, and deeper personalization.

### Retention

The code contains reflection, streak, practice, saved items, journal, festival reminders, and challenge completion loops. The retention thesis is plausible but unvalidated:

- audio is absent;
- native reminders are not verified;
- no real funnel events exist for first verse, first completion, reminder enablement, challenge join/complete, share, purchase, refund, or retention;
- there is no evidence of daily active users, week-one retention, completion rate, or qualitative feedback.

Do not claim retention until these events exist and real users exercise them.

### Monetization

The plan of record says the revenue model is a one-off finite challenge, not a subscription. The repository nevertheless contains recurring Plus monthly/annual/lifetime plans and user-facing upgrade copy. The challenge itself is blank-priced, unpublished, and empty. This creates three user harms:

1. users cannot tell what the product is selling;
2. engineering effort is split between incompatible offers;
3. a user can be asked to buy a promise that has no content.

Choose one offer before launch. The current plan supports a free daily product plus one-off dated journeys. Do not ship a subscription surface “temporarily.”

### Acquisition and shareability

Quality is only an advantage if a stranger reaches it. Current acquisition is weak:

- the static web builder is not shown as hosted;
- pages have no install/store CTA or email capture;
- no channel attribution or conversion events are present;
- the share action is account export rather than a sourced verse, festival explanation, audio card, or invitation;
- there is no evidence of App Store/Play listing optimization or acquisition testing.

The most credible acquisition artifact is a shareable, source-backed pronunciation or festival explainer that sends a user to the free app. Build that before adding more private account features.

### Operational load

Launching the current full surface would require support for:

- account and auth failures;
- content/source disputes;
- festival date disagreements;
- audio corrections;
- challenge purchase/refund/restore;
- push failures;
- AI safety/moderation and cost;
- privacy export/delete;
- tradition-sensitive complaints.

For a one-person or small team, this is too much for the current pilot. Cut Ask, subscription, and paid challenge until the free content path is trustworthy and observable.

### Viability verdict

**Viability is conditional, not demonstrated.** There is a credible product wedge and a useful offline foundation, but no demand/revenue/retention evidence and no launchable offer. The project should validate one narrow job with a free preview before committing to paid acquisition or paid content.

## 14. Prioritized action plan

### P0 — must close before any public/paid launch

1. **Freeze the pilot promise.** Hide Ask, conversation history, Plus/subscription routes, and any upgrade language from the pilot.

3. **Clear rights.** Re-source or obtain written rights for every shipped source, including excerpt/storage/embedding rights. Separate validator approval from rights approval.
4. **Finish the core trust wedge.** Add human-reviewed clear reading and slow repeat-after-me audio with accessible controls and speed adjustment if feasible.
5. **Enforce quote attribution.** Require named translator and source in the schema/validator and show both wherever a verse is quoted.

## 15. Go/no-go gates

### Free public pilot

Go only when:

- scope is visibly limited to what works;
- production config/legal/support URLs are complete;
- signed iOS and Android builds pass device acceptance;
- shipped content has source/translator/rights status that matches the UI;
- audio or a deliberately narrower non-audio promise is honest;
- festival metadata passes hard validation;
- crash/error/activation telemetry is operational and consent-safe;
- export/delete and auth recovery are tested.

### Paid challenge

No-go until all of the free-pilot gates pass plus:

- written sessions exist and are approved;
- price/refund/restore flows are tested in sandbox;
- commercial rights are cleared;
- audio is present;
- entitlement and completion state transitions are server-validated;
- customer support and correction/refund ownership exists.

### Live Ask

No-go until:

- the source corpus is rights-cleared and prepared;
- model/provider configuration is coherent;
- cache/quota/safety/audit behavior is exercised in a live environment;
- moderation/feedback operations have an owner;
- the feature is either in the product promise or fully hidden.
